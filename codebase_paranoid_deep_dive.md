#### The `lazyRetry` Resilience Pattern
In [`src/App.tsx#L14-L32`](file:///c:/Users/Ns8pc/Pictures/PeerChat/src/App.tsx#L14-L32), dynamic imports are wrapped in a custom resilience function:
1. When navigating to a lazy-loaded chunk (e.g. after a new production deploy where hashed filenames changed on the CDN), standard chunk import fails.
2. `lazyRetry` intercepts the error, sets a `sessionStorage` key `"chunk-reload"`, and forces `window.location.reload()`.
3. If the reload still fails, it clears the flag and rejects with `"Failed to load page after retry"` to prevent infinite reload loops.

### 3.2 Room Lifecycle & State Machine
File: [`src/hooks/useRoom.ts`](file:///c:/Users/Ns8pc/Pictures/PeerChat/src/hooks/useRoom.ts)

```
[Start Click / PIN Submit]
           │
           ▼
[Parallel Initialization]
 ├── Track A: WebSocket Channel Setup (`room:${pin}`)
 │    ├── Subscribe to Channel
 │    ├── Listen to Presence (sync, join, leave)
 │    └── Listen to Broadcast (`host-left`)
 │
 └── Track B: PostgreSQL RPC Invocation
      ├── If Host:  rpc('create_room', { p_pin, p_host_id, p_user_label: 'User 1' })
      └── If Guest: rpc('join_room',   { p_pin, p_user_id, p_max_users: 10 })
           │
           ▼
[Synchronization Rendezvous]
 ├── Wait for both Channel SUBSCRIBED and RPC Return
 ├── Channel.track({ user_id, label, is_host })
 └── Presence active -> isConnected = true
```

#### Dual-Channel Synchronization
For every active chat room, the client establishes **two distinct channels**:
1. `room:${pin}`: Presence and broadcast events (real-time user counter, host-leave notification).
2. `db-messages-${roomId}`: Postgres Change Data Capture (CDC) listening for `INSERT` operations on table `messages` where `room_id = roomId`.

#### Mobile Suspension & The 8-Second Grace Period
In [`src/hooks/useRoom.ts#L127-L181`](file:///c:/Users/Ns8pc/Pictures/PeerChat/src/hooks/useRoom.ts#L127-L181):
- Mobile browsers suspend WebSockets when the tab is backgrounded or screen locked.
- When a `leave` presence event is received, the Host creates an 8,000ms timer stored in `leaveTimersRef`.
- If the peer rejoins within 8 seconds (`join` presence event), the timer is cancelled.
- If the timer fires and the peer is still absent from `presenceState()`, the Host inserts a system notification into the `messages` table: `"<User X> left the room"`.

### 3.3 Messaging & Realtime CDC Pipeline
File: [`src/hooks/useChat.ts`](file:///c:/Users/Ns8pc/Pictures/PeerChat/src/hooks/useChat.ts)

```
User enters message & hits Send / Enter
   │
   ├── 1. Generate local UUID
   ├── 2. Optimistic UI Update: addMessage({ senderId: "self", senderLabel: userId, content })
   ├── 3. Insert into Supabase DB:
   │      INSERT INTO messages (id, room_id, sender_id: 'self-' + userId, sender_label: userId, content, type: 'message')
   │
   └── 4. If DB Insert Fails:
          Roll back local optimistic message and remove from seenIdsRef
```

#### Realtime Reception & Deduplication:
1. When PostgreSQL receives the row, CDC broadcasts the row to all channel subscribers on `db-messages-${roomId}`.
2. Receiving clients execute:
   - Check if `row.sender_id === "self-" + userId` -> **Ignore** (sender already rendered it optimistically).
   - Check if `seenIdsRef.has(row.id)` -> **Ignore** (duplicate prevention).
   - `seenIdsRef` is managed as an LRU-like set capped at `MAX_SEEN_IDS = 5000`.
   - Append to React `messages` state array.

### 4.2 Exact RPC Stored Procedures Implemented in DB

```sql
-- RPC: create_room
CREATE OR REPLACE FUNCTION public.create_room(
  p_pin TEXT,
  p_host_id TEXT,
  p_user_label TEXT
)
RETURNS TABLE (room_id UUID, user_label TEXT) AS $$
DECLARE
  v_room_id UUID;
BEGIN
  IF EXISTS (SELECT 1 FROM public.rooms WHERE pin = p_pin) THEN
    RAISE EXCEPTION 'PIN_EXISTS';
  END IF;

  INSERT INTO public.rooms (pin, host_id)
  VALUES (p_pin, p_host_id)
  RETURNING id INTO v_room_id;

  INSERT INTO public.members (room_id, user_id, user_label)
  VALUES (v_room_id, p_host_id, p_user_label);

  RETURN QUERY SELECT v_room_id, p_user_label;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- RPC: join_room
CREATE OR REPLACE FUNCTION public.join_room(
  p_pin TEXT,
  p_user_id TEXT,
  p_max_users INT
)
RETURNS TABLE (room_id UUID, user_label TEXT, member_count INT) AS $$
DECLARE
  v_room_id UUID;
  v_count INT;
  v_label TEXT;
BEGIN
  SELECT id INTO v_room_id FROM public.rooms WHERE pin = p_pin;
  IF v_room_id IS NULL THEN
    RAISE EXCEPTION 'ROOM_NOT_FOUND';
  END IF;

  SELECT count(*) INTO v_count FROM public.members WHERE room_id = v_room_id;
  IF v_count >= p_max_users THEN
    RAISE EXCEPTION 'ROOM_FULL';
  END IF;

  v_label := 'User ' || (v_count + 1);

  INSERT INTO public.members (room_id, user_id, user_label)
  VALUES (v_room_id, p_user_id, v_label);

  RETURN QUERY SELECT v_room_id, v_label, (v_count + 1);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

## 6. The Hidden GitHub Action: Supabase Keep-Alive Engine
File: [`.github/workflows/keep-supabase-alive.yml`](file:///c:/Users/Ns8pc/.github/workflows/keep-supabase-alive.yml)

The repository includes a dedicated 271-line CI workflow running 3 times per week at non-standard, randomized times:
- `17 4 * * 1` (Mondays 04:17 UTC)
- `43 11 * * 3` (Wednesdays 11:43 UTC)
- `5 19 * * 6` (Saturdays 19:05 UTC)

### Simulation Steps Executed by GitHub Actions Runner:
1. **Secret Check:** Verifies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`.
2. **User Selection:** Queries table `ka_users` for active test users.
3. **Session Creation:** Inserts a fake session in `ka_sessions` with randomized user agents and spoofed private IPs (`10.x.x.x`).
4. **Activity Logging:** Posts a `"login"` action event into `ka_activity_log`.
5. **Dashboard Browsing:** Performs `SELECT` queries across `ka_users`, `ka_settings`, and `ka_activity_log`.
6. **Profile Editing:** Patches `ka_users` with random rotating developer bios and random login counts.
7. **Settings Upsert:** Upserts preferences (random themes: `dark`, `light`, `system`, `contrast`; random languages: `en`, `fr`, `de`, `es`, `ja`) into `ka_settings`.
8. **Logout & Session Purge:** Deletes the created session and purges expired sessions.
9. **Housekeeping:** Purges activity logs older than 30 days.
10. **Health Check:** Runs a final query against `ka_users` to confirm database vitality.
